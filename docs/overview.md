## 一、它是什么

**一句话：古琴打谱工具——把看不懂的老谱，变成能弹的曲子。**

> 「打谱」是琴人行话：把减字谱变成能弹的音乐（行话「小曲打三月，大曲打三年」说的就是它）。
> 用行话命名的好处看「AI 释谱」就知道——**名字本身就是解释**，不用再翻译一遍。
> 「AI 释谱」的终点是看懂（输出印出来的谱）；太音的终点是弹出（输出能弹、能听、能改的曲子）。

再说得准一点——古琴谱（减字谱）记的不是音符，是**动作指令**：哪根弦、按第几徽、哪个手指、怎么弹。一个方块里塞四个信息。会弹的人读得懂；不会弹的人对着一本谱，一个字也用不上。

我们做的是这中间的转换器：**从「看不懂的方块字」到「能弹、能听、能改、能发出去的谱」。**

### 一个具体的场景

你手上有一本老《古琴曲集》，里面是减字谱。你不会弹，也读不懂。过去只有三条路：

| 办法 | 代价 |
|---|---|
| 找老师一句一句教 | 钱付给老师，一首学几个月 |
| 找人代打成可读的谱 | 一首 3–5 个工作日，改一稿再等一轮 |
| 自己对着图一个字一个字敲进电脑 | 要装 Windows 软件、装专用字体，Word 里一换字体就乱码 |

现在多了一条：**把那页拍下来传上去，它认出每个字，你逐个校对一遍，出来一份能弹能听的谱**——能导出成图、导出成音频、转成简谱给只看得懂简谱的人，也能转成一行文本码发给琴友。

**所以它不是输入法**（输入法要你先会弹），**也不是编辑器**（编辑器也要你先会弹）。
它是编辑器**前面那一步**——你还不会的时候，怎么进来。

## 二、要做成什么样子

分三层看，产品在做的是同一层的事：**让减字谱从「图片」变成「数据」。**

```
① 引擎层（已成）：减字是数据 —— 弦、徽、指法、音高，可计算
② 入口层（2/3 + 1 受限）：敲键盘 ✅ / 简谱翻译 ✅ / 图片录入 ⚠️ 受限（识别单元错配，见下）
③ 出口层（4/4） ：四种出去方式 —— 出图 / 出声 / 出码 / 出谱
```

一旦减字是数据，后面所有事才有意义：能播、能改、能转简谱、能排指法、能搜、能溯源。
反过来说，**凡是把减字当图片处理的做法，做完了都只能看，不能用**——这是我们在第十八章里看到的、十八年学术路线走不通的根因。

### 形态：不做 APP，做「打开就能用」

| 形态 | 状态 | 为什么 |
|---|---|---|
| **网页** | ✅ 已在线 | 底座。任何时候都是完整可用的 |
| **PWA** | ✅ 已落地 | 「添加到主屏」+ 断网能开，解决「没装上」的感觉 |
| **微信小程序** | ⚠️ 三页壳已做，**未发布** | 用户在微信里，小程序是顺手的入口 |
| 原生 APP | ❌ 不做 | 要写两套、过审核、长期维护。**触发条件**：小程序跑出稳定日活，用户主动要 |
| 桌面端 | ❌ 不做 | 我们的优势就是「不用装」 |

**终局形态**：在任何地方看到一首减字谱——书上、论文里、琴馆墙上、老师发的图——都能把它变成能弹的东西。手机上、电脑上、微信里，都是同一个东西。

## 三、目标

**不是做一个软件，是把「读古琴谱」这件事的门槛拆掉。**

| | 现在 | 目标 |
|---|---|---|
| 谁能用谱 | 会弹的人（他们本来就看得懂） | **想弹的人**（不用先学会） |
| 谱是什么 | 图片，只能看 | 数据，能弹能听能改 |
| 一首老谱到能弹 | 几个月（跟老师）或几天（找人打） | 自己就能走完（录入 + 逐字校对） |

判目标是否达成，只看一件事：**一个完全不会弹古琴的人，能不能自己把一本谱变成能弹的东西。**
现在还不能（见第五节），但整条链上的活都已经通了。

## 四、现在完成多少

**先说结论：工具侧接近完成，产品侧刚开始。** 这就是「一直在在路上」的真正原因——工具长了一年，产品还没出门。

### 工具侧（按条目数，不按感觉）

| 环节 | 完成 | 说明 |
|---|---|---|
| 入口：敲键盘 | ✅ | 点选 + 连打（`ad9f6cg4` = 大九六分绰勾四）+ 拼音 |
| 入口：简谱翻译 | ✅ | 自动排指法，给候选和取舍理由 |
| 入口：图片录入 | ⚠️ **受限** | 整页切分 + 逐格校正已通，但模板索引认不了标准完整减字（见下「识别能力」） |
| 出口：出图 | ✅ | PNG / SVG（矢量）/ PDF |
| 出口：出声 | ✅ | 播放、WAV、MIDI |
| 出口：出码 | ✅ | 减字文本码，纯 ASCII，记事本就能传 |
| 出口：出谱 | ✅ | 转简谱（±2 八度） |
| 练习：慢练 | ✅ | 分句、连弹三遍、档位、进度记在本机 |
| 练习：节拍器 / 调音器 / 录音 / 跟弹判定 / 日课 | ✅ | |
| 查：音位 | ✅ | 一个音列出全部弦徽位 |
| 查：字典 / 释义 | ✅ | |
| 查：**谱例溯源** | ✅ | 这个字在哪首谱第几句，点一下当场试听 |
| 形态：网页 | ✅ | 在线 |
| 形态：PWA | ✅ | 断网可开（真浏览器验过） |
| 形态：小程序 | ⚠️ | 四页壳 + 七项校验（含产物同源），**未发布、未上真机**；真机准备已脚本化（`just probe-copy wx…`） |

**发布这条线也有闸门**（2026-11-09 扩展）：`node scripts/verify-publish.mjs --copy-only` 原来只扫
5 个「当前口径文件」，待发稿全程在盲区；现在扫台账（`docs/articles/material/pending-copy.json`）
里全部 `state=pending` 的稿，仓库侧 + vault 侧都扫，并进了 CI。判红口径是 fail-closed——
`drafts/` 下每个 `.md` 不入账就红；行级豁免要 `sha256 + 过期时间 + 次数上限`，
孤儿 / 超限 / 过期同样判红。判定逻辑抽在 `scripts/lib/copy-gate.mjs`，
`--self-test` 跑 25 条（含 17 条变异）证明闸门自己不会静默失效。

**定弦这条线也有闸门**（2026-11-10）：6 种定弦的名单散在四处——前端 `TuningId`、
后端 `VALID_TUNINGS`、WASM 编排的 wire 值、翻译器映射。上一轮扩到 6 种时只改了第一处，
后端白名单仍是 3 种（新调式的谱发布/筛选直接 400），翻译器又把新调式悄悄退回正调
（编排按正调、播放按外调，差半音）。现在 `node scripts/verify-tuning-contract.mjs`
静态核对四份同源，`--self-test` 跑 7 条变异，已进 CI。

边界也说清：**简谱转减字的编排引擎只建模 1=F 清乐七声，支持正调 / 蕤宾 / 慢角**。
清商 / 太簇 / 凄凉的空弦含 D♯、F♯，这套「数字 + 八度」的记谱写不出来，
所以它们只用于存谱、调音、播放；界面会明说「编排按哪个调、放回曲谱按哪个调发声」，
不静默降级。

### 识别能力（诚实版 · 2026-11-09 已判定结构性失效）

| 字高 | 逐字正确率 |
|---|---|
| 72px | 100% |
| 48px | 97.6% |
| 24px | **59.5%** |

⚠️ 这张表**只适用于识别器自己的 257 个复合字形**（本项目字体渲染后加扰动的合成
样本，训练=测试分布）。**它不是「减字谱识别准确率」，不得对外引用。**

**2026-11-09 判定**（全文见 `docs/articles/material/2026-11-09-真谱适用性判定-识别结构性失效.md`）：
生产模板索引（前端静态 + 后端同源）257 模板 / 385 文本里 **0 条标准完整减字**
（「大九勾四」= 左指 + 徽 + 右指法 + 弦），全是字体 GSUB 预烘焙的复合指法符号
（勾剔、抹勾、间勾…）。从 4 首内置曲抽 27 个真实减字跑覆盖率闸门 → **0/27**，
同源字体都 0%，证明字符串空间根本不相交。
**不是「真谱没验过」，是连编辑器自己产出的完整减字都认不出。**

- **根因**：索引从字体 GSUB 连字表生成，识别的「单元」是复合指法符号，而减字谱的
  最小单元是完整减字 —— 单元错配，结构性失效。
- **后端两条路由都已注册**（`routes.rs:194-195`），走「模板优先 + LLM 兜底」：模板分支
  用同一份索引，LLM 分支 42 条评测 exact 0% 且线上纯静态站无 key → 两条分支都堵死。
- **方向 A 已量化**（`tools/eval-jianzi/verify-full-jianzi.py` 可复现）：给对内容算法能认
  （15 个完整减字自检索全中，但属同分布闭集自匹配，不是能力结论）；可完整减字空间约
  **30 万个**、索引约 **1.6GB**、线上一次性 fetch 放大 **1169×** → 全量重建不可行；
  且静态站点匹配器无拒识门槛（白纸 / 噪点也硬返回一个减字），噪声下置信度比命中率
  更早归零。

**结论**：识别当前**不可作为产品能力或卖点**，仅保留为「电子谱面录入辅助（受限）」。
修复需重建索引为完整减字（且只能做有限常用子集）+ 必做拒识门槛，属另排工程，
**不进当前排期**。

## 七、AI 到底结合了吗

**诚实答案：用到了，但不是核心，而且有一句绝不能说的话。**

### 现在 AI 在哪

| 位置 | 干什么 | 是不是主路径 |
|---|---|---|
| 简谱转减字的**候选择优** | 算法给候选，AI 帮忙挑一个更好解释的 | ❌ 只是建议 |
| 识别的**兜底** | 模板匹配不行时才问它 | ❌ 模板优先 |

### 一句绝不能说的话

**不能说「AI 识别减字谱」。**

实测过：让大模型直接认减字，**准确率 0%**（它把 30 多个不同的字都答成了提示词里举的那个例子）。
真正能用的是模板匹配（257 个部件模板），而且它不是 AI。

顺便说清两件容易混的事：

- **自动排指法也不是 AI**。那是确定性算法，按「手好不好挪来算代价」找最优路径。能解释、能复现。
- 产品名里的「AI 传习平台」曾**名不副实**（2026-11-07 已改名为「古琴打谱工具」，见第一节——先走了「改名」这条；等 AI 解释层真做出来再谈要不要把 AI 写回名字）。

### AI 该待的位置：解释层，不做决策

等有真实用户提问了，再做这三件：

1. **释义问答**：「这个减字什么意思 / 为什么这么弹」（答案来自释义字典，AI 换成人话）
2. **编排解释**：指法排好了，AI 讲「为什么这么排更顺手」（不参与决策，只解释结果）
3. **识别歧义提示**：把候选讲成人话（必须标「建议」，不能替代逐格校正）

**不做**：让 AI 直接出谱（错了用户听不出来）、让 AI 当识别主路径（实测 0%）、把 AI 变成唯一路径（纯前端站必须「没有 AI 也完整可用」）。

**触发条件**：有用户反复问「为什么这么弹」的真实记录再做。没有这份数据，AI 就是给投资人看的故事。

## 八、Web3 有联系吗

**没有联系，而且明确不做。**

| | 决定 |
|---|---|
| 发币 | ❌ 不做 |
| NFT | ❌ 不做 |
| 钱包门槛 | ❌ 不做（古琴用户在微信里，不在钱包里） |
| 区块链存证 | ⏸ 只在一种情况下做，见下 |

**唯一可能的用途：曲谱存证。**「我整理的谱被人搬走了」是打谱这件事最真实的痛点。
但关键判断是：**这件事不需要链也能拿到 80% 的价值**——谱面哈希 + 时间戳 + 可验证签名，已经能证明「我先整理的这个」。链只解决「多方互不信任时的共同见证」，而我们的场景是「一个人 vs 搬运者」，中间没有需要中立见证的第三方。

**触发条件**：有琴馆或老师明确提出「我的谱被搬走了」，才做。
没有这个诉求，Web3 一律不进排期。**在它真的上线可用之前，也不写进对外文案。**

## 九、为什么现在显得乱

坦白说，是我们自己的问题：

1. **竞品一篇一篇来，我们一条一条改口径**。两个月里改过：入口论、编码独有、练习功能、字库全不全——每一处都是被对手资料逼出来的修正。
2. **文档按对手长，不按产品长**。`competitive-analysis.md` 有二十章，而「这是什么」一直散在 pitch 里。
3. **工具在长，产品没出门**。功能越做越深，但没有发布、没有用户、没有一篇文章。

**这份文档就是为了止住这个。** 从现在起：

- 定位变 → 改这一份
- 竞品变 → 改 `competitive-analysis.md`，**不动定位**
- 功能变 → 改 CHANGELOG，**不动定位**
- 有人问「你们是什么」→ 直接给他看这篇
