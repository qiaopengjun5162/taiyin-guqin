# P0 第一步 · 事件驱动 + 限流（实盘哨兵 cron 具体分析与清单）

> 配套：`docs/super-agent-landing-plan.md`
> 数据来源：本机 `~/.hermes/cron/jobs.json`（64 个任务，62 个启用）
> 重要更正：经核查，Hermes **已有** kanban 调度器（`dispatch_interval_seconds: 60` + `auto_decompose`）、并发上限（`gateway.api_server.max_concurrent_runs: 10`）、准入控制（`admissions` 目录）、人工批准闸门（`cron_mode: approve`）。所以"事件驱动"和"Watchdog 限流"它**已经部分具备**，本方案只补它缺的两块：**整点雷鸣群错位** + **跨 agent 的全局上游限流**。

## 二、两个真问题（不是"要重做 cron"）

| 问题 | 现象 | 根因 |
|---|---|---|
| **① 整点雷鸣群** | 13+ 任务在 :00 同秒爆发，瞬时并发打满 | 调度表达式全写成 `0 * * * *`，没错位 |
| **② 跨 agent 共享额度无全局限流** | Codex 高频时 Hermes/Telegram 被挤到 429 | 上游（Qintopia/flatkey）并发额度被多 agent 共用，没有跨 agent 的令牌桶；Hermes 的 `max_concurrent_runs: 10` 只是**单实例**排队，管不到 Codex |

> Hermes 内部的 kanban + 并发帽 + 准入控制**已经在管单实例内的事**，所以不要动它们。要补的是上面两块。

## 三、P0-1 三招具体改法（含任务名 + 建议新调度）

### 招 1：整点雷鸣群错位（低风险、立竿见影）
把 13 个 `0 * * * *` 摊到每小时前 25 分钟内的偶数分钟，**保留"近整点"语义**（资金费率/合约类监控仍需贴着整点，方便和交易所整点快照对齐），只是错开同秒。

| 原任务 | 建议新调度 | 备注 |
|---|---|---|
| 基础设施自检(infra_selfcheck) | `0 * * * *` | 保留 :00（基础设施不依赖行情快照） |
| 合约下架监控(delisting) | `2 * * * *` | 错 2 分 |
| 期现套利空间(basis_arb) | `4 * * * *` | 错 4 分 |
| 滑点验证(slippage_verify) | `6 * * * *` | |
| Priority fee监控 | `8 * * * *` | |
| Drift链上funding | `10 * * * *` | |
| 失败交易监控(failed_tx) | `12 * * * *` | |
| Jupiter路由监控(route) | `14 * * * *` | |
| Jito bundle监控 | `16 * * * *` | |
| 执行质量tracker | `18 * * * *` | |
| bStocks事件窗口 | `20 * * * *` | |
| 狗庄出货雷达 | `22 * * * *` | |
| Solana鲸鱼出货雷达 | `24 * * * *` | |

> `*/30` 和 `*/15` 类任务（新闻轰炸、快讯层、币安ETF差等）保持原样——它们本就分散在 :00/:15/:30/:45，不是 :00 独占，错峰价值不大。

### 招 2：每 2 分钟高频任务 → 换便宜模型 + 评估降频
这 3 个是额度消耗大户，且多为"拉数据 + 格式化判断"，不需贵模型：

| 任务 | 建议 |
|---|---|
| PM双买雷达(5min涨跌盘) | 路由到**最便宜模型**；确认 2 分钟精度是否必需，可降到 3–5 分钟 |
| prey雷达×HF联动(prey_hf_trigger) | 同上，便宜模型 + 评估降频 |
| Chainlink预言机更新监听(feed_watch) | 同上 |

> 改动前需与领域 owner 确认降频是否影响告警时效（链上监控通常 3–5 分钟够用，但需确认）。

### 招 3：跨 agent 全局上游令牌桶（根治 429，需服务器侧）
这是真正解决 429 的一招，但**不在 Hermes 单实例内**，而要放在所有 agent（Hermes + Codex + 其他）共用的上游入口前：

- 在 Qintopia/flatkey 账号前加一个**共享令牌桶**（token bucket）：全局并发上限 + 每 agent 配额帽。
- 额度用尽 → **排队**而非硬闯（避免 429）；单 agent 超额自动降级到兜底模型（参照 taiyin `llm.rs` 的"调不通就回退启发式"）。
- 这等于把文章里的"外部 Watchdog"落到上游层。

> 此招需服务器侧改动（代理/网关或共享限流中间件），本机 IDE 无法执行，见第四节命令清单。

## 四、应用方式与风险提示（给能登服务器的同事）

**本文件只出 spec，不改动任何运行实例。** 落地需在有服务器权限的环境执行：

1. **招 1（错位）**：在**生产实例**的 `jobs.json` 里，把上表 12 个任务的 `schedule.expr` 改为建议值（保留 `kind: cron`）。改前备份 `jobs.json`（参考既有 `jobs.json.bak-*` 习惯）。
2. **招 2（模型路由）**：在对应任务的 `model` / `provider` 字段改指便宜模型；降频需 owner 确认。
3. **招 3（全局限流）**：在 Qintopia/flatkey 入口前置令牌桶，跨 agent 共享配额。

**⚠️ 风险红线（实盘监控，务必复核）**
- 资金费率/合约/清算类任务**必须贴整点**：错位只错 2–24 分，不要错到非整点区间。
- 不要动 `cron_mode: approve`、kanban、`max_concurrent_runs`——它们已经在正常工作。
- 改完先在**非生产实例**跑一轮，确认告警时效无退化，再上生产。
- 禁用/启用的 2 个任务（OI监控快照、Morpho埋雷雷达）本次不动。
