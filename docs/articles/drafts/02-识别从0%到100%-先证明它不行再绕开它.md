> 「需要专门的减字数据，或改走『字体反查』这类非视觉路径」。

## 一、先给结论

同一批 42 个真减字，同一个后端端点：

| 路径 | exact_match | 耗时/张 | 成本 |
|---|---|---|---|
| 通用视觉大模型（deepseek-flash） | **0%** | 1.4s | 计费 |
| 字形模板匹配（非视觉） | **100%** | <1ms | 零 |

整页识别也从「只走 LLM、没配密钥直接 503」变成了确定性可用：

```
72 张合成整页 → 打真实 HTTP 端点 → 与本地预测逐格比对
整页一致 72/72，逐格一致 851/851
```

同一天我还顺手把前端覆盖率从 71.9% 补到 94.4%——然后发现
**给我算覆盖率的工具本身在说谎**：129 行代码被静默踢出了分母，
92.5% 是虚高的。这条插曲和识别的故事共享同一个教训，放在第四节。

一句话总结这一天：**识别 0% 的问题不在管线、不在提示词，
而是问题本身问错了对象——电子谱面不需要「看懂」，只需要「认出」；
认出是查表，不是理解。**

## 二、先把尺子做准：从 10 条到 42 条

上一篇的基线只有 10 条手写真值，「exact 0%」很容易被一句「样本太小」噎回来。
先扩样，再下结论。

手工标注 42 个字形又慢又容易错（后来证明我真写错了一个）。
换了个思路：**字体的 GSUB 连字表本身就是真值库**。
每个合成字形（如 `lg_yangtuo`）记录了它的构件序列（仰+托），
反读过来就是标注——零人工、可无限扩、完全可复现。

```bash
$ python3 gen_font_cases.py
[gen] lg_dazhai      -> 打摘  (53 KB)
[gen] lg_qcsans      -> 掐撮三声  (58 KB)
[gen] md_3           -> 三弦  (14 KB)
[gen] xl_santan      -> 三弹  (81 KB)
[gen] 写了 42 条标注 -> annotations/font_cases.json
```

（`xl_santan` 我手工标的是「三声」，GSUB 反查说是「三弹」——查了字形，是对的。人手写真值真的会错。）

然后拿这 42 条去跑真识别。数字比 10 条版还难看，但**失败模式第一次清楚了**：

```text
  exact_match   = 0.0%
  mean_cer      = 1.193
  component P/R/F1 = 13.8% / 13.7% / 13.7%

lg_dazhai      ref=打摘         pred='大七勾一'
lg_qblers      ref=掐拨剌二声    pred='散挑一'
lgw_quanfu     ref=全扶         pred='散挑一'
md_5           ref=五弦         pred='五'
```

看出来了吗？它不是「认错」，是**在复读提示词里的示例**（「散挑一」是提示词给的 few-shot 样例），
外加把复合减字拦腰砍断只认下半截（五弦→五）。30 多条的答案是同一个「散挑一」。
这叫**模板坍缩**：模型没见过减字谱，就把输出坍缩到它见过的示例形状上。

更致命的是置信度：

```text
confidence [0.8,1.0): n=17  exact=0.0%
```

**最自信的 17 条，全错。** 任何「置信度低于阈值就丢弃」的过滤策略都救不了它。

到这一步，「换模型试试」已经不值得做——同一家族的通用视觉模型面对没见过的
封闭符号集，坍缩方式都一样。42 条的统计意义够了：**这条路（电子谱面问视觉模型）可以关掉了。**

```text
5b1d4d5  feat(eval): 真值改 GSUB 连字反查自动产出，42 条基线定论视觉模型不可用
```

## 三、认出，不是理解：模板匹配 0% → 100%

既然电子谱面是**本项目自己的字体**渲染出来的，那识别就不是开放世界视觉问题，
而是**闭集查表**：字体里一共 268 个可读字形（213 个复合减字 + 55 个部件），
每个渲染一张模板，归一化成 64×64 墨迹向量，来图切边、归一化、最近邻——结束。

```bash
$ python3 template_match.py build
[build] 索引 268 个模板 -> .cache/template_index.npz
$ python3 template_match.py predict --annotations annotations/font_cases.json
$ python3 score.py --offline --annotations annotations/font_cases_tpl.json
```

```text
  exact_match   = 100.0%
  mean_cer      = 0.000
  component P/R/F1 = 100.0% / 100.0% / 100.0%
```

同一批图，0% → 100%，CER 1.193 → 0.000，1.4s 计费 → <1ms 零成本。
不是调出来的，是**换了问题**。

### 坑：加一点噪声，命中率掉到 78.6%，三档完全相同

我给图加椒盐噪声测鲁棒性，0.5%/1%/2% 三档命中率**一模一样**都是 78.6%。
第一反应是中值滤波没起作用。打印归一化中间量才发现真凶：
噪点把远处的背景像素翻黑 → **墨迹外接框被撑到整图** → 字形被缩到角落里。

三档同值恰恰因为这不是「噪声强度」问题，而是「有没有一个离群噪点」的问题——
只要有一个，外接框就毁了。

改法：归一化第一步加 3×3 中值滤波（干净图上近乎恒等）。

```text
条件            命中 / 42
noise-0.5       42   100.0%   ← 去斑之后
noise-1         41    97.6%
noise-2         39    92.9%
shift/blur/scale     42   100.0%
```

**去斑是必需预处理，不是可选项。**

### 坑：测试红了，结果是测试自己写错

Rust 移植时「平移不变性」测试红了，但两张归一化结果肉眼一致。
差点去怀疑浮点实现。打印中间图才发现：4×4 小墨块的角被中值滤波**腐蚀成菱形**，
而第二张图的方块贴着画布边缘——边缘钳位让它少掉两个角。
两张图从一开始形状就不同，「平移不变」的前提被测试自己破坏了。

**测试失败时，先怀疑观测手段和测试本身，再怀疑实现。**

接进后端后走真实 HTTP 复测：42/42，且置信度 [0.8,1.0) 桶 42/42——
这次的置信度是 top-2 距离差，**真的可信**，不像视觉模型那样高置信度全错。

```text
bcaa0b2  feat(recognize): 模板匹配非视觉路径，电子谱面识别 exact 0%→100% 并接入后端
```

## 四、量尺子的工具也在说谎

（这一节和识别无关，但和识别共用一个教训。）

补覆盖率的过程本身没太多可说的——把键盘、WAV 导出、主页面这些没测过的关键路径
补成能变红的断言，覆盖率从 71.9% 一路抬到 92.5%。可写的是收尾那一刻：

覆盖率输出里有一行不起眼的日志：

```text
Failed to parse file:///.../src/lib/taiyin-wasm.ts. Excluding it from coverage.
```

**整个 WASM 桥接文件（129 行）被静默踢出了覆盖率分母。**
原因小到可笑：vitest 配置里 alias 用对象写法，`"@": ./src` 排在 `"@/wasm"` 前面，
键顺序先匹配先赢，`@/wasm/...` 被解析到了错误的路径 → 覆盖率工具解析失败 →
剔除分母 → 报告照常输出，只是数字虚高。报告上看不出来。

改成数组形式（精确前缀在前）+ 补 10 条 WASM 桥接测试后：

```text
Test Files  26 passed (26)
     Tests  298 passed (298)
Lines : 94.44% ( 1276/1351 )
  taiyin-wasm.ts   |   96.07 |    81.81 |   100 |   97.91
```

这是五个月里第 N 次遇到同一种失败：**工具静默降级，报告面不改色。**
和「模型空输出被解析成 null」「图片路径错就当空」是一类问题。
我对这类问题现在只有一个处置：要么正确，要么大声报错。

```text
3c294aa  test(web): 修覆盖率虚高（alias 顺序静默剔除 taiyin-wasm），行覆盖 92.5%→94.4%
```

## 五、整页：三起三落

单字 100% 之后，整页识别（一整张谱图切成字格再逐格认）看起来只是工程活。
实际干了一天，摔了三跤。

**第一跤：gap 曲线不单调。** 合成整页（真字体渲染拼网格）扫字格间隙，
预期「间隙越大越好切」，实测 gap=4 反而只有 56%：

```text
gap   张数  结构对  逐格exact
2     12    10      163/176 (92.6%)
4     12     7      122/217 (56.2%)   ← 反而最差
8     12    12      209/214 (97.7%)
```

我先怀疑合成图的重采样失真，设计了三组对照实验（原图直接 / LANCZOS 缩小 / magick 重渲），
结果 98.6% / 96.7% / 96.2%——几乎一样，**假说被证伪**。
把失败字格裁出来看，真凶现形：**一个字被切成了两三个框**。

复合减字内部本来就有白色通道（上下部件之间、左右象限之间），
裸投影「一列白就切」把内部通道当成了字格间隙——**切过头，不是切不开**。

改法是间隙容忍投影：白缝小于阈值不切。阈值不拍脑袋，量了 213 个真字形的
内部白缝分布（列向 p99=2px、max 4px），而真 app 的字格间隙是 0.5×字高，
中间余量充足 → 阈值取 0.10×S（S=页面墨迹尺度）。

**第二跤：行向阈值照搬单字测量，把行全粘住了。**
单字的内部横通道可以到 0.36×字高，我按 0.40×S 取——结果 gap<0.4 的行全连成一片。
错在统计单元：行投影横跨整行所有列，单个字的内部通道会被同行其他字的墨盖住，
只有整行对齐才误切。行、列最终都取 0.10×S。

**第三跤：192px 的大字还有 3 个错。** 字号再大不该有信息丢失了。
一查模板距离：

```text
一徽二分(sm_1.2) vs 十二徽(sm_12): 模板距离 0.000
十一徽(sm_11)   vs 一徽一分(sm_1.1): 模板距离 0.000
```

**距离 0.000——字体把这两个名字画成了同一个轮廓**，任何算法都分不开。
这是字形库的固有歧义，不是识别错误。处理：索引合并等价簇（truths 取并集），
「命中任一等价写法即对」。另外 `md_3`（三弦）和 `sm_3`（三徽）都是光板「三」，
也是视觉等价写法，同样合并。268 个模板合并成 257 个条目。

三跤摔完，数字定格：

```text
gap/字高  张数  结构对  逐格exact
0.1       12    12      196/197 (99.5%)
0.5       12    12      208/210 (99.0%)   ← 真 app 的间隙比例
```

- 切分：间隙 ≥0.2×字高全对；真 app 是 0.5×字高（5 倍余量）
- 逐格 exact：字高 ≥72px 时 42/42 = 100%；48px 97.6%；24px 59.5%（小字信息丢失，识别整页请用 ≥3× 导出）
- Python ↔ Rust 双端一致：72/72 页、851/851 格逐位相同
- 3 轮变异验证（把桥接/列序/兜底改坏各一次）确认新测试真的会红

```text

```

## 六、这一天我更确信的三件事

### 1. 先证明它不行，再绕开它

如果 0% 的时候就急着换模型、调提示词，我会在「调不动的模型」上耗很久，
而且永远说不清「是模型不行还是我不行」。先用 42 条真值把它**钉死在 0%**、
把失败模式（模板坍缩、置信度倒挂）钉清楚，换路才换得理直气壮。

### 2. 测量工具本身要被测量

eval 的真值会写错（xl_santan），覆盖率工具会静默剔除分母，测试自己会破坏前提。
这一天里「尺子出问题」的次数比「被测对象出问题」还多。
所以每个测量工具我都留了回环测试：模板自匹配必须回同名、
Python/Rust 同一批图必须逐格一致、覆盖率分母要单独核对过。

### 3. 边界要诚实量化，比「准确率 100%」更有用

模板匹配的 100% 有明确前提：同一字体渲染的干净图，字高 ≥72px。
拍照、扫描件、小于 48px 的字——不在 100% 的适用范围内，写清楚，然后把
不适用的情况交给 auto 模式自动落 LLM。**一个写明边界的 100%，
比一个没有边界的 95% 可信。**

## 最后

上一篇写完，有人说「识别才 23.8% 怎么就发了」。这篇就是回答：
**先把差写清楚，再把变好也写清楚。** 0% 和 100% 都是真的，中间隔着的不是玄学，
是四步：把尺子做准 → 把对象钉死 → 换一个问题 → 把边界量出来。

古琴减字谱在数字世界里几乎没有位置，这件事没变。
变的是：现在至少有一小块——干净的电子谱面——能被机器**准确无误**地认回来了。
