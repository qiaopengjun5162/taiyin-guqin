# CI 连红四轮没人发现：识别面板把「试听」整个藏了（2026-11-08）

## 意图

首访修复（`b9fd0bc`）推完，去查「文章群发前线上会不会自动更新到这版」。
按项目纪律「触发了的 workflow 必须全绿」看了一眼 CI，结果撞见一个跟本次改动
完全无关的旧伤：`build` **从 11-07 傍晚起连续 4 次 run 全是红的**
（`a1fb6c98` / `7dd9fa6f` / `645d2609` / `b9fd0bc`，全是同一条断言），
而 `Deploy to GitHub Pages` 每次都 success，所以四轮都被当成
「部署成功 = 一切正常」放过去了。

## 输入

- `gh run view 42440103619 --log-failed`（前一笔的 build 失败日志）

关键事实：散音 bug 修好后，「散勾」这种缺弦序的输入不再返回**半残对象**，

> 字明明认出来了，按钮凭空消失，页面上连一句「为什么没声音」都没有。

测试注释还写着旧行为「解析得出减字，但无法反推频率」，从那天起一直红。

3. 修法（按「解释 > 静默」，不是把断言改松）：

- 抽 `canListen = freq != null && 简谱 != null`，按钮 disabled / 说明 / 合成三处共用
  一个判据，消掉「按钮能点、下面却写着算不出音高」的自相矛盾；
- `currentText = (edit ?? glyph ?? "").trim()`：有字但拼不成谱字时**保留灰掉的试听**
  并写明「还拼不成可弹的谱字，请补全弦序、徽位」；校正框清空时仍完全不显示
  （原用例 `queryByText("试听")).toBeNull()` 守住）；
- `handlePlay` 复用组件里算好的 `previewFreq`，不再重复调一次。

## 卡点

- **最容易走错的一步是把测试断言改松**（既改成「按钮不存在」）。那样 CI 立刻绿，
  但产品缺口留着：用户识别出一个字，界面什么都不解释。先判断「是断言过时还是
  UI 退步」，再决定改哪边。
- **误判方向**：grep 到文案还在，第一反应是「条件分支没进」，方向对；但真正原因
  不在组件，是上游 `parseJianziText` 的语义变了。跨模块的旧伤要靠实测返回值定位，
  光读组件读不出来。
- **部署成功 ≠ CI 全绿**：`build` 与 `Deploy to GitHub Pages` 是并行 workflow，
  Pages 用上一次成功的产物也能部署成功。只看部署状态会漏掉挂掉的质量闸门。

## 结论（可引用）

- 「修好一个 bug 可能会让另一个断言变红，而那条红不是噪音，是在报告**新的 UI 行为**。」
  散音解析不再返回半残对象 → 组件原来的 `state &&` 从「显示灰按钮」变成「整块消失」。
- 面板类产品的一条原则：**不能静默地少给一个控件**。信息不全时宁可留一个灰按钮 +
  一句原因，也别让用户猜「是不是没识别出来」。
- 「按钮能不能点」和「下面那句音高说明」必须用同一个判据算，否则会自相矛盾。
- 流程：push 后要按 headSha 逐个查**所有被触发的 workflow**，不能只看部署结果。
