# 首访走查：「先听一首」原来只给看，不给听（2026-11-08）

## 意图

上一轮三件都卡在等人 / 等素材（文章群发、真手机、真谱照片）。用户回「继续」。
这轮挑一件**不等人、又直接服务「出门」**的事：文章一发出去就会有陌生人点进来，
而 0.40.0 新加的首页「太音是什么 → 先听一首 → 开始打谱」这条首访路径，
从没被当成真人完整点过一遍。上一轮只截图核过首屏对比度，没走过链路。

## 输入

- `apps/web/src/app/page.tsx`：「太音是什么」介绍区（空谱显示），两个按钮
- `apps/web/src/lib/use-score-player.ts`：播放 hook（`play` 为 `useCallback`，依赖 `notes`）
- 三个线上/本地入口：dev `localhost:3100/taiyin-guqin`、GitHub Pages、Vercel
- 上轮只验过三个 URL 的 HTTP 200 与 `<title>`，**没验过内容**

## 卡点

- **dev server 静默服务旧编译**：第一次浏览器探针显示 `AudioContext 创建次数: 0`、
  播放键仍「播放」，零报错。差点去改逻辑，看后台日志才发现 Turbopack 报
  `Broker request outcome unknown: write EPIPE`（沙箱文件代理写失败），HMR 没生效。
  **重启 dev server 后一次通过**。教训：改完代码浏览器「没生效」，先重启再怀疑逻辑。
- **`--autoplay-policy=no-user-gesture-required` 是后门**：起初顺手加了这个 flag，
  等于绕过真实策略，测了也白测。去掉后拿到 `state: running` 才是真结论。
- **`getByLabelText` 不是 Playwright API**（是 Testing Library 的），应为 `getByLabel`。
- **测试环境连锁问题**：`handlePlay` 联动节拍器导致 `use-metronome.ts` 抛
  `ReferenceError: AudioContext is not defined`（unhandled rejection）。
  这不是单纯补 mock 能了事的——它同时暴露了「点听一首会连节拍器一起响」的产品问题，
  于是直接调 `play()` 绕过联动，测试和体验一起修好。
- **forks 池四个 worker 全部启动超时（240s）**，本机旧病加重；
  改 `--pool=vmThreads` **单文件逐个跑**（组合跑会跨文件泄漏 `vi.mock`）。
- hydration mismatch 只在 dev 出现（服务端 `caret-color` 样式客户端没有），线上三环境零报错，
  非本轮改动引起，未动。

## 结论（可引用）

- **HTTP 200 不等于页面对**。静态 SPA 的正文靠 JS，链接上线前要用真浏览器看内容，
  尤其文章/宣传里发出去的链接。
- **文案是承诺，按钮是履约**。「先听一首」点完没声，比没有这个按钮更伤：
  新访客第一次相信你，就被糊弄了一次。功能验收要按「名字承诺了什么」去点，
  不能只核「有没有渲染出来」。
- **演示场景不要背练琴偏好**：默认联动节拍器对练琴是对的，对「听一首」是噪音。
- **自动播放这类改动，单测证明不了**：jsdom 里 `AudioContext` 是假的、autoplay 策略不存在。
  必须补一层真浏览器探针（创建次数 / state / 实际排程音源数），且不开策略后门。
- 三层验证定式：真浏览器行为 → 单测 + 变异验证 → lint/tsc。
