# 2026-10-29 · 拿 Hermes 的 key 接上视觉识别，并量出第一份准确率

## 1. 意图

项目里 AI 减字识别一直处于「代码写了、没人真跑过」的状态——缺一个 Anthropic key。
用户手里有 Hermes，让我「看看 Hermes 用什么，拿过来用」。同时想确认：这条链路到底能不能用，
准确率是多少（而不是继续「感觉能用」）。

## 3. 操作与真实输出

### 3.1 先查模型清单，而不是猜

```bash
curl -s --noproxy '*' -H "Authorization: Bearer $KEY" \
  https://api.deepseek.com/v1/models
```

```json
{"data":[
 {"id":"deepseek-flash","name":"DeepSeek-V4.1-Flash","input_modalities":["text","image"]},
 {"id":"deepseek-v4-pro","name":"DeepSeek-V4-Pro","input_modalities":["text"]}]}
```

这一步是全流程的转折点：**同端点下只有一个型号能吃图**。

### 3.2 选错型号的表现：不报错，只是「看不见」

用 `deepseek-v4-pro`（纯文本）喂一张 120×120 纯红方块：

```text
A) 纯红方块 问颜色: 200 -> '看不到'
B) 减字图 问内容: 200 -> '抱歉，我无法查看这张图片，因为图片格式不受支持或未成功上传。'
```

HTTP 200、JSON 结构完全合法、`glyph` 为 null。**这就是最恶劣的失败形态：假绿灯。**

### 3.3 换 `deepseek-flash` 后能看见，但返回空

```text
A) 纯红方块 问颜色: 200 -> '红色'              # 视觉确认可用
B) 减字"仰托":      200 -> ''                   # 能看，但没输出
```

查 `finish_reason` 与用量：

```json
{"finish":"length",
 "usage":{"completion_tokens":512,
          "completion_tokens_details":{"reasoning_tokens":512}}}
```

把预算提到 3000，推理 token 也同步涨到 3000，`content` 仍然为空 —— **不是预算不够，是思考吃光了预算**。

### 3.4 找关掉「思考」的开关

逐个试参数（同一张图、同一提示词）：

| 参数 | 结果 |
|---|---|
| `effort: "low"` | finish=stop，有输出（reasoning 1315） |
| `thinking: {"type":"disabled"}` | finish=stop，**reasoning=None，1.4s 返回** |
| `reasoning_effort: "low"` | finish=length，content 空 |
| `enable_thinking: false` | finish=length，content 空 |

关掉思考后，用项目真实提示词跑：`1.4s` 拿到合法 JSON：

```json
{"glyph":"挑七","explanation":"左侧亻为右手指法'挑'的减字写法…","confidence":0.9}
```

### 3.5 端到端跑一次真实评测

用项目自带字体按字形名渲染 10 个真减字（`gen_font_cases.py`），走真实后端：

## 4. 卡点与解决

| # | 现象 | 误判 | 根因 | 改法 |
|---|---|---|---|---|
| 1 | 识别结果 `glyph:null`、`explanation:"图片不可用"` | 以为模型不认识减字 | **选错型号**：`deepseek-v4-pro` 只吃文本，端点接受请求但不传图 | 默认模型改 `deepseek-flash`；`.env.example` 写明查 `input_modalities` |
| 2 | `content` 恒空、`finish_reason=length` | 以为 `max_tokens` 不够 | 推理型模型把预算全用于 reasoning | 默认发 `thinking:{"type":"disabled"}`；网关不认识该字段则去掉重试一次 |
| 3 | 空内容被解析成 `glyph:null` 却返回 200 | 以为「模型放弃识别」是正常业务 | `parse_recognition` 把 JSON 解析失败静默兜底 | 空内容直接 `bail!`，宁可 500 也不给假绿灯 |
| 4 | eval 报 `FileNotFoundError: annotations/images/xxx.png` | 以为图片没生成 | `annotations/` 与 `images/` 是同级目录，原逻辑只按标注文件目录解析（`--offline` 不读图，故长期未暴露） | 按「标注目录 → harness 根 → cwd」三级解析并列出尝试路径 |
| 5 | 同一张图两次跑出 `散挑一` / `大七勾一` | 以为 eval 不稳定 | 模型输出本身非确定 | 记录在 README：看趋势不看单点 |

### 顺带修正的一条旧结论

10-29 早些时候我用 1×1 红点图测 `deepseek-v4-pro`，得到「支持多模态」的结论——**是错的**。
1×1 图被模型当作无效图，返回「无法确定」，而我把「接受请求」误当成「看见了图」。
正确判据只有两个：`/v1/models` 的 `input_modalities`，以及**能答对颜色**这种可证伪的问题。

## 5. 结论与可引用点

- 管线侧：`detection_rate = 100%`、响应 `1.4–1.6s`、JSON 可解析 → **管线/环境没问题**
- 模型侧：`exact_match = 0%`、`component F1 = 23.8%`、置信度 0.8–1.0 桶仍全错
  → 通用视觉模型未针对减字谱训练，**且 confidence 不可用于阈值过滤**
- 一句话进文章：「它认得『五』，但不认得『五弦』；它给错答打 0.98 的置信度。」
