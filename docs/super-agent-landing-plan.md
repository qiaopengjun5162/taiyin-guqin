## 一、先说结论（30 秒看懂）

我们要解决两个反复咬人的问题：

| 痛点 | 现在什么样 | 文章给的招数 | 改完啥样 |
|---|---|---|---|
| 定时任务（cron） | 到点就点火（`.fire-*.lock` 满天飞），互相撞车，失败了还静默 | **事件驱动**：有活才跑，没活不占额度 | 只在真有事件时触发，不再空跑、不再撞车 |

1. cron → 事件驱动
2. Router/Worker 分模型 + 外部 Watchdog 限流

## 二、DeepSeek 文章讲了啥（大白话版）

文章没有发明新理论，是把计算机里老熟的工程思想搬到了 Agent 系统。5 个招数，用生活比喻：

| 招数 | 大白话 | 生活比喻 |
|---|---|---|
| **双层架构** | 上面一层做计划/协调，下面一层只管执行 | 项目经理 + 施工队，经理不搬砖，工人不画蓝图 |
| **事件驱动** | 不是定时去"点名"，而是"有事发生才行动" | 有客人进门才叫服务员，不是每分钟挨个问"您要点单吗" |
| **异步多信道** | 多个渠道（微信/邮件/群）的事件都汇到一条处理流，互不阻塞 | 前台收好几路电话，统一记到派单本，后厨照单做 |
| **存算分离** | 状态（图纸/进度）存外面，干活的进程可以随时换 | 图纸存在档案室，哪个工人请假，换个人照图纸接着干 |
| **外部 Watchdog** | 有个"监工"盯着：限流、超时、兜底、报警 | 电梯限载 10 人，满了就排队，不让人硬挤导致卡死 |

文章的核心判断：**瓶颈已经从"模型能不能干"变成了"人的注意力够不够"**。系统把繁琐的会话管理、上下文同步接管掉，人就能从"盯执行"上移到"做决策、做验收"。

## 三、映射到我们的真实痛点

| 文章招数 | 我们现在的现状（已验证） | 解决什么 |
|---|---|---|
| 事件驱动 | Hermes `cron/` 目录全是 `.fire-*.lock` 一次性定时点火文件；到点就跑，不管有没有活 | 空跑浪费额度；多个任务同时点火撞车 |
| Router/Worker 分模型 | 多个 agent（Hermes 各 profile、Codex）共用**同一个上游 API 的并发额度**；Codex 高频时 Hermes/Telegram 被挤到 429 | 互相抢额度，低频服务被高频拖死 |
| 外部 Watchdog | 之前靠"人去盯 cron wrapper 的 stdout/stderr 才发现异常" | 失败静默，发现太晚 |
| 存算分离 | 上下文/状态散在各 agent 进程里，某个挂了要重来 | 难恢复、难扩展 |
| 双层架构 | 目前是"单层和模型直聊"，没有计划层/执行层区分 | 所有任务一个待遇，简单活也占贵模型 |

**好消息**：太音自己的 `crates/taiyin-server/src/llm.rs` 已经是一个**正确样本**——默认用便宜的 `claude-haiku-4-5` 做减字候选选择，调不通就回退启发式 top1，并支持 OpenAI 兼容网关。这正好是"Worker 用便宜模型 + 兜底"的雏形，P0 方案二要把这个思路提到 agent 编排层。

## 四、P0 方案一：cron → 事件驱动

### 现在的问题
- `cron/` 里每个 `.fire-*.lock` 是一个"到点就点火"的一次性任务。
- 不管有没有真正要处理的内容，到点就跑一轮，白耗 API 额度。
- 多个任务在同一时刻点火，瞬间打满上游并发 → 429。
- 某次跑挂了只写进 stdout/stderr，没人盯就静默丢失。

### 改法（三步走）
1. **加一个事件入口（Event Bus）**
   - 把"时间到了"这个触发条件，换成"事件发生了"。事件来源举例：
     - 微信群收到新素材 / 新消息 → 入队
     - 文件/目录发生变化（如新曲谱上传到太音）→ 入队
     - 上游 webhook 回调 → 入队
   - 实现可轻量：先用 Postgres 的一张 `events` 表当队列（我们本来就跑着 Postgres），不必一上来就上 Redis/Kafka。

2. **cron 降级为"兜底巡检"**
   - 不删 cron，而是把频率调低（如从每 5 分钟一次改成每 1 小时一次），只负责"万一事件漏了，兜底补一遍"。
   - 这样即使事件通道暂时故障，也不会完全停摆（保留回滚安全网）。

3. **事件处理器只处理"有活"的任务**
   - 处理器从 `events` 表取一条 → 执行 → 标记完成/失败。
   - 失败写进同一张表（带错误栈），由 Watchdog 统一报警，不再散落 stdout。

### 收益
- 没活不跑 → 直接少一大截空耗额度，429 概率下降。
- 事件串行消费 → 不再瞬间并发撞车。
- 失败有迹可循 → 不用人工盯日志。

## 五、P0 方案二：Router/Worker 分模型 + 外部 Watchdog

### 现在的问题
- 所有 agent 共用同一个上游 API 的并发额度。
- Codex 高频执行任务时，把额度占满，Hermes/Telegram 这类低频但重要的服务拿到 429，毫无预兆地整体断掉。

### 改法（分三层）

**第 1 层 · Router（分诊台）**
- 每个请求先过 Router：判断"这事难不难、急不急"。
- 简单/高频的执行类任务（如格式转换、模板匹配、批量识别）→ 路由到**便宜模型**（参考 taiyin 的 haiku 思路）。
- 复杂/低频的规划类任务（如排期决策、内容策划）→ 路由到**贵模型**。

**第 2 层 · Worker（执行队）**
- 贵模型 Worker 设并发上限（如同时只跑 2 个），便宜模型 Worker 可以放宽。
- 贵模型只接"难且值得"的活，自然不会被高频执行淹没。

**第 3 层 · Watchdog（监工/限流）**
- 全局并发配额由 Watchdog 统一看守。
- 额度满了 → **排队**，而不是让请求硬闯拿到 429。
- 单 agent 设独立并发帽，防止某一个（如 Codex）把全局额度吃光。
- 超时/连续失败 → 自动降级到兜底模型（就像 taiyin llm.rs 的"调不通就回退启发式"）。

### 收益
- Codex 的高频执行走便宜模型 + 排队，不再抢占 Hermes 的额度。
- Hermes/Telegram 低频但重要的调用有了并发帽保护，不再被挤爆。
- 即使上游偶发限流，也"优雅排队"而非"整体 429 断联"。

### taiyin 可立即复用的样本
`llm.rs` 里已经是这个模式的微型版：
```rust
// 默认便宜模型，失败回退启发式
const DEFAULT_MODEL: &str = "claude-haiku-4-5-20251001";
// 调用失败 → 调用方回退到启发式 top1
```
把它"升级"成编排层通用能力即可，不必从零写。

## 七、风险与回滚

| 风险 | 应对（已在设计里埋好） |
|---|---|
| 事件通道故障，任务漏跑 | cron 降级为"兜底巡检"保留，低频补跑，不会全停 |
| Router 分诊误判，难活被扔给便宜模型 | Watchdog 兜底：连续失败/超时就升舱回贵模型 |
| Watchdog 自身挂了 | 限流默认"放行"（fail-open），最坏回到现在状态，不会比现在更糟 |
| 改错生产配置 | 所有变更走受控脚本 + 配置备份（参考 `~/.hermes/config.yaml.bak-*` 的既有备份习惯） |
