## 结论先行（三句话）

1. **网页端不缺功能，缺的是"手机上的入口"。** 调音器、节拍器、录音、慢练、日课、导出、整页识别
   全都在网页端跑着——旧文档把它们排成"以后要补"，照那个排期会重复造轮子。
2. **小程序是唯一值得现在做的形态。** WASM 已验（模拟器 PASS），三页壳已落地，
   但**未发布、未上真机**。下一步是「拍照识别 + 真机验证」，不是重写。
3. **AI 只做解释层，Web3 只做存证。** 两者在拿到真实需求信号前都**不进排期**；
   而 AI 更有一条硬边界：**LLM 直接识别减字，实测 exact 0%**。

## 一、现在用户怎么用太音，卡在哪

- **形态**：网页应用，核心逻辑编译成 WASM 在浏览器里跑；曲谱库可选（Postgres）。
- **部署**：GitHub Pages + Vercel 双免费托管，长链接、无独立域名、无应用商店、无搜索曝光。
- **三个真痛点**（用户原话"上手太难、没人用"拆开）：
  1. **找不到**——只在文章里丢链接；
  2. **不会用**——首屏是"选音色→点指法→点弦徽"，对路人是重交互；
  3. **没"装上"的感觉**——手机浏览器一关就没了，无留存。
- 本轮新增的**小程序壳**解决的是第 2、3 条的一半（有"打开就有"的形态、首屏只有两个入口），
  但**没发布就没有第 1 条**——用户仍然找不到它。

## 二、竞品参照与定位（压缩版）

| 谁 | 一句话 | 形态 | 有没有"识别" |
|---|---|---|---|
| 忘机减字谱 | "我认真做谱" | 专业打谱工具，桌面内测 | ❌ |
| 如意谱斋 | "我手写谱" | 桌面打谱软件 | ❌ |
| 丝桐里 | "我手机输入谱" | 移动 APP（输入/练习/调音/节拍/音位图） | ❌ |
| 丝桐（2018，已停运） | "我陪你一句一句练" | 纯 iOS（免费，域名已失效） | ❌ |
| 火蜘蛛输入法 | "我敲键盘出谱" | Windows 输入法（IME） | ❌ |
| 古琴和音 | "我小程序里拍照译谱" | 微信小程序 | ⚠️ 有，但锁在微信生态 |
| **爱搜减字** | "我手写一个字查它" | 网页（2015，免费） | ✅ **单字检索**（候选/释义/出处） |
| **华夏古琴网** | "我手写/拍照查指法" | 微信小程序（2021，免费） | ✅ **单字检索**，**且已有小程序** |
| **太音** | **"我拍一下就听"** | 网页（+ 小程序在做） | ✅ 浏览器内零安装 |

**推论（三条，按重要性）**

1. **"入口"这个位子不是空的，但"整页"是空的**：丝桐里/火蜘蛛/忘机都是"输入向"，要求用户**已经会打谱**；
   爱搜减字（2015）、华夏古琴网（2021）确实是"免输入"，但只到**单字检索**——给候选、释义、视频，不产出谱。
   **我们做的是"整页 → 一首能弹的谱"**，这一层至今没人做（详见竞品文档第十七章）。
2. **但"轻"这个位子被火蜘蛛占了半边**：它 400 万字库 + 在线增量下发 + 会员版，
   在"输入"这条路上已经很硬。**别跟它比字库和输入便利**，比不过也不必要。
3. **⚠️ "小程序 + 识别"这个组合 2021 年就有人占了**：华夏古琴网小程序（免费）手写/拍照查指法，
   古琴和音在小程序里做拍照译谱。**所以不能说"只有我们在小程序里做识别"。**
   真正的差异在**输出**：它们给「这个字什么意思」，我们给「整首能弹、能听、能改的谱」。
   ⚠️ 而我们自己的小程序版**还没有识别功能**（只有三页壳），别对外混着讲。

## 三、三条路对比

### 路线 A：微信小程序 —— 最高优先级

**⚠️ 技术路线更正（第二版给的是 Taro，实际没走，理由如下）**

| 旧判断 | 实际做法 | 为什么改 |
|---|---|---|
| Taro 4.x 编译 React 组件，省一半工 | **原生小程序 + WASM Worker** | ① 减字渲染是「字体 GSUB 连字 + 手绘 SVG」双层，React 组件复用的前提是小程序能跑这两层，实际卡在自定义字体与内联 SVG；② MVP 只需要"纯计算 + 列表"，没有复杂交互，复用收益小；③ `WXWebAssembly` **只在 Worker 内可用**，原生壳能直接把 wasm 放进去（探针已验） |
| — | 代价：UI 要重写 | 实际约一天（三页），比跟 Taro 的编译差异搏斗便宜 |

- **为什么它仍是最优先**：用户全在微信（文章在微信发、琴友在微信聊），小程序是"顺手"的入口；
  能被搜到、能转发、能扫码。
- **现状**：`apps/miniprogram-wasm-probe` 已有 home / 查音位 / 记一个字 三页，
  Node 侧 34 项行为断言 + 5 个校验器全绿；**未发布、未上真机**。
- **坑**：类目选"工具/教育"；WASM 要分包；**开发者工具 CLI 不接受游客 AppID**，
  模拟器只能 GUI 手动开（想自动化截图得先有测试号）。

### 路线 B：PWA —— 已落地（2026-11-07）

- **做了什么**：`app/manifest.ts`（standalone、宣纸底色、maskable 图标）+ `public/sw.js`
  （三档策略）+ `components/pwa-register.tsx`（仅生产注册）。图标不是通用图形，
  是用站内真减字谱字体渲染的「散勾三」，四张 PNG 已提交。
- **收益落在哪**：首屏要拉 1.1MB 减字字体 + 270KB WASM + 1.4MB 模板索引（合计约 2.9MB）。
  缓存后二次打开几乎零等待，且**断网仍能打开、翻已看过的谱**——练琴时手机没信号是常态。
- **验证**：本地起静态服务（模拟 GitHub Pages `/taiyin-guqin/` 子路径），Playwright 实测 12 项，
  含「断网后 reload 仍能打开且页面有真实内容」。**不是"构建通过就当成了"。**
- **三条保守取舍**（都是为了让 SW 不会把用户钉死在旧版本上）：
  HTML 走 network-first；只有带哈希的 `/_next/static/` 走 cache-first；
  字体/wasm/图标/数据这类「URL 不变、内容会变」的走 stale-while-revalidate。
- 局限没变：iOS Safari 支持弱（无安装横幅）；应用商店搜不到。
- **判断**：这是"救急"，不是长期形态。小程序仍是主线。

### 路线 C：原生 APP —— 不做

要写两套、过审核、长期维护，成本最高见效最慢。**触发条件**：小程序跑出稳定日活、用户主动要 APP。

## 五、小程序「拍照识别」的可行性（先算清，再立项）

不靠感觉，逐项核过：

| 项 | 实测 / 核对结果 | 结论 |
|---|---|---|
| 模板索引 | `crates/taiyin-server/data/template_index.json` **1.3 MB**（等价 257×64×64 = 1.05 MB 原始字节） | **必须放分包**（主包 2 MB / 总分包 20 MB） |
| 网页端实现 | `apps/web/src/lib/jianzi-template.ts` 10 KB，**13 处依赖 canvas / ImageData** | 搬进小程序要换纯像素数组或 wx canvas，**不是改路径** |
| 整页切分 | Rust 有 `sheet_segment.rs`，浏览器版是 TS 另写的一份 | 小程序要么再移植 TS，要么把 Rust 版导出到 wasm（后者更稳，但要动 wasm 导出面） |
| 精度 | 字高 72px exact 100%、48px 97.6%、24px **59.5%** | **必须配逐格校正**；不配就只能对 ≥3× 的清晰图承诺 |
| 验收口径 | 网页端早已如实标注"拍图识别 + 逐格校正" | 小程序沿用同一口径，别另发明说法 |

**工程量判断**：**3–5 天**级别（分包 + 像素管线 + 校正 UI），不是"改个配置就能跑"。
**顺序建议**：真机验现有三页 → 再做识别。理由见第四节的门槛。

## 六、后端上云（做曲谱库才绕不开）

- **能纯前端跑完的**：识别、编排、播放、导出、查音位、日课——**全部不需要后端**。
- **必须后端的**：跨设备同步、多人协作、社区发布/收藏。
- **硬约束（工程）**：纯前端模式（GitHub Pages、无 `NEXT_PUBLIC_API_URL`）下曲谱走 localStorage；
  任何新增后端依赖功能**必须同时设计静态站降级**，否则线上"点了报错"。
- **何时上云**：只在阶段 3。选型按已有实现走（axum + Postgres 已就绪），别为小程序换一套技术栈。

## 七、AI 这块怎么做（新增）

### 7.1 先把现状说清，因为它决定 AI 的位子

- 仓库里 `llm.rs` 的角色是**识别候选的兜底**，不是主路径。
- **实测：让 LLM 直接识别减字，exact 0%**（模板坍缩——30+ 条答案都是提示词示例），
  它给的 `confidence` 也不可信。
- 模板匹配 + `auto`（模板优先）路径是 **100%**。

→ **所以对外不能说"AI 识别减字谱"**。这句话既不符合事实，也正好撞口径红线第 2 条。

### 7.2 值得做的三件（都在"解释层"，不改变计算结果）

| # | 做什么 | 为什么安全 | 成本 |
|---|---|---|---|
| 1 | **释义问答**：「这个减字什么意思 / 为什么这么弹」 | 答案有标准来源（现有释义字典），AI 只负责换成人话 | 低（文本） |
| 2 | **编排解释**：DP 已经算出最优路径，AI 讲"为什么这么排" | **不参与决策**，只解释既有结果 | 低 |
| 3 | **识别歧义提示**：把候选排序讲成人话 | 必须标注"建议"，不能替代逐格校正 | 中 |

### 7.3 绝不能做的四件

1. 让 LLM **直接出谱 / 出音**——不可验证，错了用户听不出来是错的；
2. 让 LLM 当**识别主路径**——实测 0%，且比模板慢、比模板贵；
3. 把 API key 下发到前端——纯前端模式没有秘密；
4. 让 AI 成为**唯一路径**——纯前端站必须能"没有 AI 也完整可用"。

### 7.4 触发条件

有用户反复问"为什么这么弹 / 这句怎么排"的**真实提问记录**，再做第 1、2 件。
没有这份数据，AI 就是给投资人看的故事，不是给琴友用的功能。

## 八、Web3 这块怎么做（新增）

### 8.1 不做清单（先划红线）

- ❌ **不发币、不做 NFT 炒作、不设钱包门槛**——古琴用户在微信里，不在钱包里；
- ❌ **不把"区块链存证"写进对外文案**，直到它真的上线可用（口径红线第 4 条：
  方向已规划但未落地，提前写就是虚假宣传）；
- ❌ 不把"上链"当成宣传卖点本身——**链是给信任用的，不是给叙事用的**。

### 8.2 可做的三件（按价值排序）

| # | 做什么 | 解决什么 | 依赖 |
|---|---|---|---|
| 1 | **曲谱存证与署名**：谱面哈希 + 时间戳，必要时上链 | "我整理的谱被人搬走了"——打谱这件事最真实的痛点 | 可先只做「哈希 + 本地时间戳 + 公开可查」，**链是可选后端** |
| 2 | **传承谱系记录**（师承 / 流派 / 版本） | 古琴极重师承，谱的"来源"本身有文化价值 | 需要内容侧数据，非技术问题 |
| 3 | **赞赏 / 打赏** | 打谱者变现 | 走微信支付 / 小程序虚拟支付，**与链无关，别混为一谈** |

### 8.3 关键判断

第 1 件的价值**不需要区块链也能拿到 80%**：公开的哈希 + 时间戳 + 可验证签名，
已经能证明"我先整理的这个谱"。**链只解决"多方互不信任时的共同见证"**，
而我们的场景目前是"一个人 vs 搬运者"，中间没有需要中立见证的第三方。

→ **触发条件**：有琴馆/老师明确提出"我的谱被搬走 / 被盗用"的诉求，才做第 1 件；
没有这个诉求，Web3 一律不进排期。

## 九、明确不做清单（防止被愿景带跑）

1. **不和忘机卷做谱深度**——它投了一年多排版引擎，正面竞争必败且无意义。
2. **不和火蜘蛛卷字库与输入便利**——它 400 万字库 + 在线增量，这条路它已经赢。
3. **不做桌面端分发**（百度网盘 / 软件管家 / 装机量）——我们的分发优势就是"不用装"。
4. **不做多字体**（梧冈/梅庵/龙吟馆等）——双渲染层都要平行重做；
   而且**做多字体最多的那家（火蜘蛛）自己说第三种字体"没啥卵用"**（见竞品文档 12.10）。
5. **不做原生 APP**——等小程序留存说话。
6. **不发币、不做 NFT**——见 8.1。
7. **不把 PWA 当长期方案**——它只是过渡，做完就停，不要再往上叠功能。
8. **不在小程序里重建网页端的编辑/播放/导出**——那些是网页端的活，
   小程序只做"轻用"（查、记、拍、听）。

## 十、风险与回滚

| 风险 | 应对 |
|---|---|
| 小程序审核被拒 | 类目选"工具/教育"，提前备功能说明；被拒改类目重提 |
| 真机上 WXML 布局崩坏 | 先做阶段 1 的真机验证门槛，不过不叠识别 |
| WASM 在低版本基础库不可用 | 探针已记边界；上线前划定最低基础库版本并给降级提示 |
| 云费用失控（阶段 3 起） | 按量计费 + 限额告警；纯前端模式几乎零费用 |
| 多端维护人力 | 只维护"网页 + 小程序"两端；APP 不碰 |
